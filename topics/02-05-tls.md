# 05 — TLS

> Part 2 — Networking & Communication · Prerequisites: topics 03, 04

TCP delivers bytes reliably, but in plain text, and anyone on the path (a Wi-Fi hotspot, an ISP, a
compromised router, a misconfigured proxy) can read them or change them. DNS, as topic 04 showed, can be
spoofed, so you can't even be sure the address you connected to belongs to the right server. **TLS**
(Transport Layer Security; its predecessor was SSL) fixes both problems: it encrypts and
integrity-protects the byte stream, and it proves the server is who it claims to be.

For system design, TLS matters in three ways. It **costs round trips and CPU** at connection setup,
which shapes connection reuse, edge termination and protocol choice (topics 03, 06, 14). It relies on
**certificates**, whose issuance, rotation and expiry are an operational job that causes real outages.
And **where you terminate it** decides what your load balancers can see and which parts of your network
carry plain text.

By the end of this topic you should be able to:

1. Say what TLS provides (confidentiality, integrity, authentication) and which part of the handshake
   provides each.
2. Walk through a TLS 1.3 handshake and explain why it needs one round trip where TLS 1.2 needed two.
3. Explain certificates and the chain of trust: how a client decides to trust a server, and how that
   trust is issued, revoked and audited.
4. Explain forward secrecy and why ephemeral key exchange provides it.
5. Explain session resumption (IDs, tickets, PSKs) and 0-RTT, including why 0-RTT is only safe for
   replayable requests.
6. Compare TLS termination options (edge, re-encrypt, passthrough, mutual TLS) and their trade-offs.

---

## 1. What TLS provides

TLS sits between TCP and the application, and gives the application three properties:

1. **Confidentiality**: an observer on the path can't read the data.
2. **Integrity**: tampering is detected; modified, reordered or truncated data is rejected.
3. **Authentication**: the client knows it's talking to the real `api.example.com`, not an impostor.
   Optionally the server can verify the client too: **mutual TLS (mTLS)**, common between internal
   services (topic 10).

Note what TLS does *not* hide: the IP addresses and ports (TCP/IP headers are outside it), the size and
timing of messages, and, in most deployments today, the hostname the client asks for (section 3, SNI).

### The building blocks, briefly

You don't need the mathematics, but you do need to know what each tool is for:

| Tool | What it does | Cost | Used for |
|---|---|---|---|
| **Symmetric encryption** (AES-GCM, ChaCha20-Poly1305) | Same key encrypts and decrypts. The "AEAD" variants also attach an authentication tag, so tampering is detected. | Very cheap; AES has hardware support in modern CPUs | All the actual data |
| **Key exchange** (Elliptic-Curve Diffie–Hellman, ECDHE) | Two parties each send a public value and both compute the same shared secret, which an eavesdropper can't compute | Moderate | Agreeing on the symmetric keys |
| **Digital signatures** (ECDSA, RSA, Ed25519) | Prove a message was produced by the holder of a private key; anyone with the public key can verify | Signing moderate-to-expensive, verifying cheap | Proving identity; certificates |
| **Hash functions** (SHA-256) | Fixed-size fingerprint of data | Cheap | Signatures, deriving keys, transcript checks |

The pattern: **expensive public-key operations happen once, in the handshake, to agree on keys;
cheap symmetric encryption protects everything after.** That's why TLS's cost is concentrated at
connection setup.

## 2. The handshake: what it establishes

Before encrypted data can flow, the two sides must agree on:

- the **TLS version and cipher suite** (which algorithms to use);
- a set of **shared secret keys**, which nobody watching the exchange can work out;
- the **server's identity**, proven by its certificate and a signature.

### TLS 1.3, step by step

```
Client                                                        Server
  │  (TCP handshake already done: 1 RTT)                         │
  │                                                              │
  │── ClientHello ──────────────────────────────────────────────▶│
  │     versions, cipher suites, SNI = api.example.com,          │
  │     ALPN = [h2, http/1.1], key share (client ECDHE public)   │
  │                                                              │ picks suite, makes its own
  │                                                              │ ECDHE pair, computes shared
  │                                                              │ secret, derives keys
  │◀───────────────────────────────────────────── ServerHello ───│
  │     chosen suite, key share (server ECDHE public)            │
  │   { EncryptedExtensions (ALPN = h2)                          │  everything in { } is
  │     Certificate (chain)                                      │  already encrypted
  │     CertificateVerify (signature over the handshake so far)  │
  │     Finished (MAC over the handshake) } ─────────────────────│
  │                                                              │
  │ computes shared secret, derives keys,                        │
  │ verifies the certificate chain and the signature,            │
  │ checks Finished                                              │
  │── { Finished } + { HTTP request } ──────────────────────────▶│
  │◀────────────────────────────────────────── { HTTP response }─│
```

What each piece establishes:

- **Key exchange → confidentiality.** Each side generates a fresh, temporary (**ephemeral**) ECDHE key
  pair and sends the public half. Combining your own private half with the other side's public half
  gives both sides the same secret. An eavesdropper who sees both public halves can't compute it. Both
  sides derive symmetric keys from that secret.
- **Certificate + CertificateVerify → authentication.** The certificate says "this public key belongs to
  `api.example.com`", vouched for by a CA (section 3). But anyone can copy a certificate; it's public.
  The proof is **CertificateVerify**: the server signs a hash of the whole handshake so far with the
  certificate's private key. Only the real owner can produce that signature, and because it covers
  this handshake's random values and key shares, it can't be replayed from another session. This is
  also what stops a man-in-the-middle substituting its own key share.
- **Finished → integrity of the handshake.** Each side sends a MAC over the full transcript. If an
  attacker tampered with any handshake message (say, stripping strong cipher suites to force a weak
  one, a **downgrade attack**), the transcripts differ and the handshake fails.
- **AEAD record protection → integrity of data.** After the handshake, every record carries an
  authentication tag and an implicit sequence number. Modified, dropped or reordered records fail
  verification and the connection is torn down.

Why only one round trip? In TLS 1.3 the client **guesses** which key-exchange group the server will
accept and sends its key share in the very first message. The server can finish the key agreement in
its first reply, so the client can send its request with its own Finished. (If the guess is wrong, the
server replies with a **HelloRetryRequest** and it costs an extra round trip, which is rare in
practice because almost everyone supports X25519.)

### TLS 1.2 for comparison

```
TCP + TLS 1.2 (fresh)                       TCP + TLS 1.3 (fresh)

Client                    Server            Client                    Server
  │── SYN ───────────────▶│                   │── SYN ───────────────▶│
  │◀──────────── SYN-ACK ─│  1 RTT            │◀──────────── SYN-ACK ─│  1 RTT
  │── ACK, ClientHello ──▶│                   │── ACK, ClientHello ──▶│
  │◀── ServerHello, cert ─│  2 RTT            │   (+ key share)       │
  │── key exchange, Fin ─▶│                   │◀── ServerHello, cert, │  2 RTT
  │◀─────────────── Fin ──│  3 RTT            │    Fin (+ key share) ─│
  │── HTTP request ──────▶│                   │── Fin, HTTP request ─▶│
  │◀───── HTTP response ──│  4 RTT            │◀───── HTTP response ──│  3 RTT
```

- **TLS 1.2** negotiates first and exchanges keys second: **2 round trips** of handshake on top of TCP's
  one.
- **TLS 1.3** collapses that to **1 round trip**. It also removed old, weak options (static RSA key
  exchange, CBC-mode ciphers, compression), so every TLS 1.3 handshake has forward secrecy, and it
  encrypts the certificate so observers can't see which certificate the server presented.

At 100 ms RTT, a fresh HTTPS request over TLS 1.2 spends 300 ms on setup before the request is even
sent. TLS 1.3 saves 100 ms of that. QUIC (topic 06) saves another 100 ms by merging the transport and
TLS handshakes.

### Forward secrecy

**Forward secrecy** means that if the server's long-term private key is stolen later, an attacker who
recorded past traffic still can't decrypt it. It comes from the ephemeral key exchange: session keys
are derived from temporary ECDHE key pairs that are thrown away after the handshake. The long-term key
is used only to **sign** (prove identity), never to derive the session keys.

Contrast old-style RSA key exchange (allowed in TLS 1.2, removed in 1.3): the client encrypted the
session secret with the server's long-term public key. Anyone who later obtained the private key could
decrypt every recorded session. That's the scenario forward secrecy exists to prevent.

### SNI and ALPN

Two small fields in the ClientHello matter a great deal for infrastructure:

- **SNI (Server Name Indication)**: the client says which hostname it wants *in the first handshake
  message*, before any certificate is chosen. That lets one IP address host many sites with different
  certificates, which is how load balancers and CDNs serve thousands of domains from shared IPs. It
  also lets an L4 proxy route a TLS connection by hostname without decrypting it (section 6). SNI is
  sent in clear text today; **Encrypted Client Hello (ECH)** is an extension that hides it.
- **ALPN (Application-Layer Protocol Negotiation)**: the client lists the application protocols it
  speaks (`h2`, `http/1.1`), and the server picks one inside the handshake. This is how HTTP/2 is
  negotiated with no extra round trip (topic 06).

## 3. Certificates and the chain of trust

Key exchange alone gives you an encrypted channel to *someone*. Authentication answers "to whom?". A
man-in-the-middle could happily do a key exchange with you and another with the server, relaying
between them. Certificates are what stop that.

### What a certificate contains

A certificate (format: **X.509**) is a small signed document. The fields that matter:

```
┌───────────────────────────────────────────────────────────────┐
│ Subject / SAN:   api.example.com, www.example.com             │  names this key is valid for
│ Public key:      ECDSA P-256 04:a3:...                        │  the server's public key
│ Issuer:          Example Intermediate CA R3                    │  who vouches for it
│ Validity:        2026-09-01 → 2026-11-30                       │  not before / not after
│ Key usage:       digital signature; server authentication      │  what it may be used for
│ Extensions:      CA = false; CRL / OCSP URLs; CT timestamps   │
├───────────────────────────────────────────────────────────────┤
│ Signature:       issuer's signature over everything above      │
└───────────────────────────────────────────────────────────────┘
```

The certificate is **public**. Having a copy proves nothing; what proves identity is holding the
**private key** that matches the public key inside it (demonstrated by CertificateVerify). This is why
the private key is the thing to protect, and why where it lives (section 6) is a security decision.

Names are checked against the **Subject Alternative Name (SAN)** list. A **wildcard** like
`*.example.com` matches exactly one label (`api.example.com`, not `a.b.example.com`). One certificate
can list many names, which is how a load balancer covers many services with one certificate.

### The chain

The server's certificate (the **leaf**) is usually not signed directly by a root CA. It's signed by an
**intermediate CA**, whose certificate is in turn signed by a **root CA**:

```
   ┌──────────────────────────┐
   │ Root CA                  │  self-signed; shipped in the OS / browser
   │ "Example Root X1"        │  "trust store". Private key kept offline.
   └────────────┬─────────────┘
                │ signs
   ┌────────────▼─────────────┐
   │ Intermediate CA          │  sent by the server in the handshake.
   │ "Example Intermediate R3"│  Does the day-to-day signing.
   └────────────┬─────────────┘
                │ signs
   ┌────────────▼─────────────┐
   │ Leaf: api.example.com    │  sent by the server in the handshake.
   └──────────────────────────┘
```

The client verifies by walking **up** the chain:

1. Is the leaf's signature valid under the intermediate's public key? Is the intermediate's signature
   valid under the root's public key?
2. Is the root in my **trust store** (the list of root certificates shipped with the OS, browser or
   language runtime)? Trust has to start somewhere, and this is where: a few hundred roots,
   pre-installed.
3. Is each certificate within its validity period? Is each intermediate actually allowed to act as a
   CA? Are the key usages right?
4. Does the requested hostname match one of the leaf's SAN entries?
5. Has any certificate in the chain been revoked (as far as the client checks; see below)?

If all of that passes and the CertificateVerify signature checks out, the client has a chain of
signatures from something it already trusted down to "this key belongs to `api.example.com`, and the
peer holds that key".

**Why intermediates?** The root's private key is enormously valuable: compromise it and you can
impersonate any site. So it's kept offline in a hardware security module and used rarely, only to sign
intermediates. Intermediates do the daily signing; if one is compromised, it can be revoked and
replaced without changing every trust store in the world.

**A classic failure: the missing intermediate.** The server must send the intermediate(s) along with
its leaf. If it sends only the leaf, some clients (browsers that cached the intermediate earlier, or
fetch it themselves) work fine, while others (mobile apps, API clients, other servers) fail with
"unable to verify certificate". The symptom is "works in my browser, fails from the service".

### How certificates are issued

A CA must check that whoever requests a certificate for `api.example.com` actually controls that name.
For ordinary (**domain-validated**) certificates, this is automated, usually with the **ACME** protocol
(popularised by Let's Encrypt):

1. The requester generates a key pair and asks the CA for a certificate for `api.example.com`.
2. The CA issues a challenge: put this token at `http://api.example.com/.well-known/acme-challenge/...`
   (HTTP-01), or publish it in a DNS TXT record `_acme-challenge.api.example.com` (DNS-01).
3. The CA checks the token from its own vantage points, and if it's there, signs the certificate.

Note the dependency: certificate issuance trusts DNS and routing (topic 04). Whoever controls your DNS
can get certificates for your names. DNS-01 is also the only way to get wildcard certificates, and works
for servers that aren't reachable from the internet.

Internally, organisations often run a **private CA**: their own root, trusted only by their own
machines, used to issue certificates for internal services and for mTLS client identities.

### Revocation: taking trust back

If a private key leaks, the certificate must stop being trusted before it expires. Mechanisms:

- **CRLs (Certificate Revocation Lists)**: the CA publishes a signed list of revoked serial numbers.
  Simple, but lists grow and clients must fetch them.
- **OCSP**: the client asks the CA "is this certificate still good?". Adds a lookup on the critical
  path, and tells the CA which sites users visit (a privacy problem). **OCSP stapling** has the server
  fetch a signed, time-limited OCSP response and include it in the handshake, removing the extra
  lookup.

In practice revocation checking is weak: many clients **soft-fail** (if the revocation check can't be
completed, they proceed anyway, since otherwise an attacker who blocks the check gets a denial of
service), and browsers use their own curated revocation lists. Some CAs (Let's Encrypt among them) have
dropped OCSP altogether in favour of CRLs.

The industry's answer is **short-lived certificates**: if a certificate is only valid for days or weeks,
a stolen key is useful only briefly, even if revocation is never checked. Let's Encrypt issues 90-day
certificates (and shorter options), and the CA/Browser Forum has scheduled the maximum lifetime of
public certificates to shrink in steps, down to 47 days by 2029. The consequence for operations is that
**certificate renewal must be fully automated**.

### Certificate Transparency

What if a CA is compromised or careless, and issues a certificate for your domain to someone else? It
has happened (DigiNotar in 2011 is the famous case). **Certificate Transparency (CT)** makes issuance
public: CAs submit every certificate to append-only public logs (built on Merkle trees, topic 53), and
browsers refuse certificates that don't carry proof of being logged. Domain owners can monitor the logs
and spot certificates for their names they didn't request.

### Expiry: the outage you can schedule

Certificates expire on a known date, and expired certificates cause hard failures: every client refuses
to connect. Expired certificates have taken down large services many times, often an internal or less
visible one (an API gateway, an internal CA's intermediate, a certificate embedded in a device or a
mobile app). The defences are boring and effective: automated renewal well before expiry, monitoring of
expiry dates on every endpoint (including internal ones), and alerting weeks ahead.

A related trap: **certificate pinning** (an app accepting only one specific certificate or key) makes
rotation dangerous; if the pinned key changes, pinned clients break until they're updated.

## 4. The cost: round trips and CPU

**Latency.** On a fresh connection, TLS adds one round trip (TLS 1.3) or two (TLS 1.2) on top of TCP's
one, before the first request. Resumption and 0-RTT (section 5) reduce this; connection reuse (topic 03)
avoids it entirely for every request after the first.

**CPU.** The public-key operations in the handshake (the server's signature, the ECDHE computations,
the client's chain verification) are far more expensive than encrypting bulk data, which modern CPUs do
in hardware at many gigabytes per second per core. So:

- A server handling **many new connections per second** spends noticeable CPU on handshakes. This is
  what a flood of new connections (a reconnect storm after a deploy, or an attack) costs.
- A server with **long-lived connections** barely notices TLS.
- The certificate's key type matters: an ECDSA signature is much cheaper for the server to produce than
  an RSA-2048 one, so ECDSA certificates reduce handshake CPU.

**Bytes.** The certificate chain is a few kilobytes. On a fresh connection it competes with slow start's
small initial window (topic 03), so a bloated chain can cost an extra round trip. Keep chains short.

The overall lesson: **TLS's cost is per connection, not per byte.** "TLS is too slow for internal
traffic" is usually a statement about connection churn, not about encryption.

## 5. Session resumption and 0-RTT

If a client has talked to a server recently, it can skip most of the handshake.

### Resumption mechanisms

- **Session IDs** (TLS 1.2): the server remembers the session's keys under an ID; the client presents
  the ID next time. Downside: the server must store state, and behind a load balancer the next
  connection may land on a server that doesn't have it (unless servers share a session cache).
- **Session tickets** (TLS 1.2) and **pre-shared keys / PSKs** (TLS 1.3): the server encrypts the
  session state with a **ticket key** that only servers know, and hands the blob to the client to store.
  Next time the client presents it; any server holding the same ticket key can decrypt it and resume.
  This works well behind a load balancer: it's the stateless-vs-stateful theme from topic 01, with the
  client carrying the state.

Resumption saves the certificate exchange and the expensive signature and verification work. In TLS
1.3 a resumed handshake is still one round trip unless 0-RTT is used, and it normally still does a
fresh ECDHE exchange alongside the PSK (the `psk_dhe_ke` mode), keeping forward secrecy.

**The ticket key is a sensitive secret.** Anyone who has it can decrypt tickets, and with TLS 1.2
tickets (or TLS 1.3 PSK-only resumption) that means decrypting the sessions resumed with them. Ticket
keys must be shared across the server fleet (for resumption to work behind a load balancer), **rotated
frequently** (hours, not months), and never written to disk carelessly. Otherwise a long-lived ticket
key quietly undoes forward secrecy.

### 0-RTT ("early data")

In TLS 1.3, a client resuming with a PSK can send application data **in its very first flight**,
encrypted with keys derived from the PSK, before the handshake finishes:

```
Client                                                   Server
  │── ClientHello + PSK + key share                        │
  │   + { early data: GET /products/42 } ─────────────────▶│  can start processing
  │◀──────────── ServerHello ... Finished ─────────────────│  immediately
  │◀──────────── { response } ──────────────────────────────│
```

Over TCP that saves one round trip; with QUIC (topic 06) the request reaches the server with **zero**
round trips of setup.

The catch is serious: **early data can be replayed.** An attacker on the path who captures the first
flight can send it again, to the same server or to another server in the fleet. The normal handshake
prevents replay because the server contributes fresh randomness before any data is accepted; 0-RTT data
arrives before the server has contributed anything.

```
 Client ──[ClientHello + PSK + "POST /transfer $100"]──▶ Server A   (processed)
                     │
       attacker copies the packet
                     │
                     └──────────────────────────────────▶ Server B   (processed again!)
```

Servers can reduce replay (accept each ticket only once, keep a cache of recently seen ClientHellos,
reject early data outside a short time window), but doing that perfectly across a distributed fleet
requires shared state, which is exactly what tickets were meant to avoid. So the standard position is:
**TLS cannot guarantee 0-RTT data isn't replayed; the application must only accept it for requests that
are safe to repeat.**

In practice:

- Allow 0-RTT only for **idempotent** requests (topic 07): a `GET` that reads data, never a payment, an
  order, or any state change whose repetition matters (topic 38 covers idempotency in depth).
- A front-end that terminates TLS and receives early data can forward it to the backend with an
  `Early-Data: 1` header; a backend that doesn't want to risk it replies **`425 Too Early`**, and the
  client retries after the full handshake.
- Early data also has weaker forward secrecy: it's protected only by the PSK-derived keys, not by a
  fresh key exchange.

## 6. Where TLS ends: termination

"Terminating" TLS means being the endpoint that holds the private key, completes the handshake and
decrypts the traffic. Where you do it is an architectural decision:

```
Option A: terminate at the edge, plain text inside
  Client ══TLS══▶ [LB / CDN edge] ──plain HTTP──▶ App servers

Option B: terminate and re-encrypt
  Client ══TLS══▶ [LB / CDN edge] ══TLS (internal cert)══▶ App servers

Option C: passthrough (L4, route by SNI without decrypting)
  Client ══════════TLS══════════▶ [L4 proxy] ════════════▶ App servers (hold the key)

Option D: mutual TLS between services
  Service A ══mTLS (both present certs)══▶ Service B
```

| | Edge termination (A) | Re-encrypt (B) | Passthrough (C) | mTLS (D) |
|---|---|---|---|---|
| Handshake RTTs over the short user-to-edge path | Yes | Yes | No (to the backend) | n/a (internal) |
| LB can read HTTP (route by path, add headers, cache, WAF) | Yes | Yes | No | Depends on where it ends |
| Plain text on the internal network | Yes | No | No | No |
| Where private keys live | Edge only | Edge + backends (internal certs) | Every backend | Every service (its own identity) |
| Backend CPU for handshakes | None | Some (amortised over long-lived connections) | All of it | Some |

Why terminate at the edge? The expensive handshake round trips happen over the **short** user-to-edge
path (a CDN site in the user's city, topic 14), the edge can keep long-lived, warm connections to the
origin, and the load balancer can do L7 work: route by path or header, add headers, retry, cache
(topics 09, 10). The costs: the edge holds your private keys (a CDN terminating TLS for you holds your
keys or keys for your names), and the backend no longer sees the client's TCP connection, so the client
IP and the original protocol must be passed along in headers like `X-Forwarded-For` or the PROXY
protocol.

Why re-encrypt? "The internal network is trusted" has repeatedly proven untrue: a compromised host,
a misconfigured mirror port, or an attacker who has got inside can read plain-text internal traffic.
Encrypting internal hops is increasingly the default, and modern hardware makes it cheap as long as
connections are reused.

**Mutual TLS** goes further: both sides present certificates, so the server knows *which service* is
calling, not just that the channel is encrypted. That turns the network identity into an authentication
mechanism (topic 54). Doing it by hand for hundreds of services, each with its own certificates and
rotation, is hard, which is a large part of why service meshes exist: sidecar proxies terminate and
originate mTLS, and the mesh's control plane issues and rotates short-lived certificates automatically
(topic 10).

## 7. How it connects

- **Topic 03**: TLS adds round trips and CPU on top of TCP's handshake, making connection reuse even
  more valuable; the certificate chain competes with slow start's initial window.
- **Topic 04**: TLS is the backstop for DNS spoofing: a forged DNS answer can't produce a valid
  certificate. In the other direction, CAs validate domain control via DNS.
- **Topic 06**: ALPN negotiates HTTP/2 inside the TLS handshake; QUIC builds TLS 1.3 into the transport
  so the transport and crypto handshakes take one round trip together, and makes 0-RTT practical.
- **Topic 07, 38**: 0-RTT is only safe for idempotent requests, the same property that makes retries
  safe.
- **Topics 09, 10, 14**: load balancers, gateways, meshes and CDNs are where TLS is terminated, and
  where mTLS between services is managed.
- **Topic 47**: certificate rotation is a change like any other and must be automated and monitored.
- **Topic 53**: Certificate Transparency logs are built on Merkle trees.
- **Topic 54**: mTLS is one way services authenticate each other.

## Common misconceptions

- **"TLS is too slow to use internally."** → Bulk encryption is cheap on modern hardware; the cost is
  mostly in handshakes, which connection reuse amortises.
- **"The certificate proves the server's identity."** → The certificate is public; anyone can send it.
  Proof comes from the server signing the handshake with the matching private key.
- **"Encryption means nobody can see anything."** → IPs, ports, message sizes and timing are visible,
  and SNI usually reveals the hostname.
- **"Revoking a certificate stops it from working immediately."** → Many clients don't check
  revocation reliably (soft-fail). Short certificate lifetimes are the practical defence.
- **"0-RTT is just a faster handshake."** → It changes the security properties: early data can be
  replayed, so it's only safe for idempotent requests.
- **"Session resumption is purely a performance feature."** → Ticket keys are secrets whose leak can
  expose resumed sessions; they must be rotated and protected.
- **"If it works in my browser, the certificate is configured correctly."** → Browsers can paper over
  a missing intermediate that other clients won't.
- **"Terminating TLS at the load balancer is the end of the story."** → It leaves plain text on the
  internal network and moves your private keys to the edge; both are deliberate trade-offs.

11. What does TLS 1.3 0-RTT add, and why is it only safe for some requests? Give one request that
    should be allowed in 0-RTT and one that shouldn't, and say how a backend can refuse early data.

12. Your API servers' CPU spikes after every deploy, even though request volume is unchanged. Clients
    reconnect after the deploy. What's consuming the CPU, and what reduces it?

13. Compare terminating TLS at the load balancer with plain HTTP behind it, against TLS passthrough.
    What can the load balancer do in each case, and what are the security trade-offs?

14. What does mutual TLS give you that ordinary server-authenticated TLS doesn't, and why do service
    meshes make it practical?

## Answers

<details>
<summary>Show answers (attempt the questions first)</summary>

**1.** **Confidentiality** (nobody on the path can read data): the ephemeral ECDHE key exchange produces
shared secrets that drive symmetric encryption. **Integrity** (tampering is detected): AEAD encryption
(e.g. AES-GCM) attaches a tag to every record, and the Finished messages MAC the whole handshake so
handshake tampering (like a downgrade) is caught. **Authentication** (you're talking to the real
server): the server's certificate, which chains to a trusted CA, plus CertificateVerify, where the
server proves it holds the matching private key by signing the handshake.

**2.** The certificate only binds a name to a public key. To complete the handshake, the server must
produce a **CertificateVerify** signature over this specific handshake transcript (including fresh
random values and key shares) using the **private key**. Without the private key, the attacker can't
produce that signature, and it can't replay one from an old session because the transcript differs.
Protecting the private key is what matters.

**3.** In TLS 1.2 the client and server first negotiate algorithms and only then exchange key material:
two round trips. In TLS 1.3 the client **guesses** the key-exchange group and sends its key share in
the very first message, so the server completes the key agreement in its first reply: one round trip.
If the guess is wrong, the server sends a **HelloRetryRequest** naming a group it accepts, and the
client tries again, costing an extra round trip.

**4.** **Forward secrecy** means that stealing a server's long-term private key later doesn't let an
attacker decrypt traffic they recorded earlier. It comes from **ephemeral** Diffie–Hellman key pairs
generated per session and thrown away; the long-term key only *signs*, never derives session keys. With
RSA key exchange, the client encrypted the session secret under the server's long-term public key, so a
stolen private key decrypted all recorded sessions. TLS 1.3 removed it so every connection has forward
secrecy.

**5.** The server sends its leaf certificate and intermediates. The client checks each signature up the
chain (leaf signed by intermediate, intermediate by root), checks that the root is in its **trust
store**, checks validity dates, CA flags and key usage, checks that the hostname matches a SAN entry,
and possibly checks revocation. Then it verifies the CertificateVerify signature with the leaf's public
key. Trust ultimately comes from the **root certificates pre-installed** in the OS, browser or runtime:
trust has to start from something you already have.

**6.** The root's private key can impersonate anyone, so it's kept offline in hardware and used rarely.
Intermediates do the routine, online signing. If an intermediate is compromised or must be retired, it
can be revoked and replaced without changing trust stores on billions of devices, which takes years.

**7.** The server is probably sending **only the leaf certificate, without the intermediate**. Browsers
often have the intermediate cached or fetch it themselves, so they build the chain anyway. The backend's
TLS library doesn't, so it can't connect the leaf to a trusted root. Fix: configure the server to send
the full chain (leaf + intermediates).

**8.** Revocation checking is unreliable: many clients soft-fail when they can't reach the CRL/OCSP
service (otherwise blocking the check would be a denial of service), OCSP adds latency and leaks
browsing data, and lists grow large. If certificates only live for days or weeks, a stolen key is
useful only briefly, whether or not anyone checks revocation. The demand on operations: **fully
automated issuance and renewal** (e.g. ACME), plus monitoring of expiry on every endpoint, because
manual renewal every few weeks doesn't scale and missed renewals cause hard outages.

**9.** **Certificate Transparency.** Browsers require publicly trusted certificates to be recorded in
append-only public CT logs. You (or a monitoring service) can watch those logs for any certificate
issued for your domain names, and spot one you didn't request.

**10.** With **session IDs**, the session state lives on the server that created it. The next connection
may be routed to one of the other 19 servers, which has no record of it, so a full handshake is needed
(unless servers share a session cache). With **session tickets**, the client carries the encrypted
session state itself, and any server holding the shared ticket key can decrypt it and resume, wherever
the load balancer sends the connection. New risk: the **ticket key** is a fleet-wide secret; if it
leaks, tickets (and sessions resumed without a fresh key exchange) can be decrypted. It must be rotated
frequently and protected.

**11.** On resumption, 0-RTT lets the client send application data in its first flight, using keys from
the previous session, saving a round trip. Because that first flight can be captured and **replayed**
(to the same or another server) and TLS can't reliably detect it across a fleet, it's only safe for
**idempotent** requests. Allowed: `GET /products/42`. Not allowed: `POST /payments` or "add to
cart". A terminating proxy can mark forwarded early data with `Early-Data: 1`, and the backend can reply
**`425 Too Early`**, making the client retry after the full handshake.

**12.** **TLS handshakes.** Every client reconnects at once, and each new connection needs the server to
compute an ECDHE exchange and a signature, which are far more expensive than encrypting data. Request
volume is the same, but the number of *handshakes* spiked. Reduce it with session resumption (tickets
shared across servers, so a reconnect is cheaper), ECDSA instead of RSA certificates (cheaper signing),
terminating TLS on a layer that isn't restarted with the app (a load balancer that keeps client
connections open), and spreading reconnects out (graceful draining, jittered reconnects, topic 47).

**13.** **Terminate with plain HTTP behind**: the LB decrypts, so it can route by path and headers, add
headers, retry, cache and apply a WAF, and handshakes happen near the user; but traffic behind the LB is
readable by anyone inside the network, and the LB holds the private key. **Passthrough**: the LB only
sees TCP and the SNI hostname, so it can route by IP/port or SNI but can't inspect or modify HTTP;
traffic stays encrypted to the backend, and private keys live on every backend, which also bears all
handshake CPU. A common middle ground is to terminate at the LB and re-encrypt to the backends.

**14.** Ordinary TLS authenticates only the **server**: the server knows the channel is encrypted, not
who is calling. With **mTLS** the client also presents a certificate, so the server cryptographically
knows which service is calling and can authorise on that identity. Doing it manually means issuing,
distributing and rotating certificates for every service instance. A service mesh's sidecars handle the
TLS on both ends transparently, and its control plane acts as a private CA that issues and rotates
short-lived certificates automatically.

</details>

## Flashcards

Cover the answer, say it out loud, then check.

**Q:** The three things TLS provides?
**A:** Confidentiality, integrity, authentication.

**Q:** What does TLS not hide?
**A:** IP addresses, ports, message sizes and timing, and (without ECH) the SNI hostname.

**Q:** Why does TLS use both public-key and symmetric cryptography?
**A:** Public-key operations (expensive) agree on keys and prove identity once; symmetric encryption (cheap, hardware-accelerated) protects the data.

**Q:** What proves the server actually owns its certificate?
**A:** CertificateVerify: a signature over the handshake transcript made with the certificate's private key.

**Q:** What do the Finished messages protect against?
**A:** Tampering with the handshake, e.g. downgrade attacks; each side MACs the full transcript.

**Q:** Handshake RTTs: TLS 1.2 vs TLS 1.3?
**A:** TLS 1.2: 2 RTT. TLS 1.3: 1 RTT (client sends its key share up front). Both on top of TCP's 1 RTT.

**Q:** What is a HelloRetryRequest?
**A:** The server telling a TLS 1.3 client its key-share guess was wrong; costs an extra round trip.

**Q:** What is forward secrecy?
**A:** Ephemeral Diffie–Hellman keys mean a stolen long-term key can't decrypt past recorded traffic.

**Q:** What is SNI?
**A:** The client names the hostname in its first handshake message, so one IP can serve many sites and certificates.

**Q:** What is ALPN?
**A:** Negotiating the application protocol (h2, http/1.1) inside the TLS handshake, with no extra round trip.

**Q:** What does a certificate bind together?
**A:** A set of names (SAN) and a public key, plus validity dates and usage, signed by an issuer.

**Q:** How does a client verify a server's certificate chain?
**A:** Check signatures up to a root in its trust store, validity dates, CA flags, hostname match, (maybe) revocation.

**Q:** Where does trust ultimately come from?
**A:** Root certificates pre-installed in the OS, browser or runtime trust store.

**Q:** Why use intermediate CAs?
**A:** Root keys stay offline; intermediates do daily signing and can be replaced without changing trust stores.

**Q:** Symptom of a missing intermediate certificate?
**A:** Browsers work, other clients (services, apps) fail with "unable to verify" errors.

**Q:** How does ACME prove domain control?
**A:** The CA asks for a token at an HTTP URL on the domain (HTTP-01) or in a DNS TXT record (DNS-01).

**Q:** CRL vs OCSP vs OCSP stapling?
**A:** CRL: published list of revoked serials. OCSP: client asks the CA per certificate. Stapling: server attaches a signed OCSP response to the handshake.

**Q:** Why are certificate lifetimes getting shorter?
**A:** Revocation is unreliable (soft-fail), so short lifetimes limit how long a stolen key is useful. Requires automated renewal.

**Q:** What is Certificate Transparency?
**A:** Public append-only logs of every issued certificate; browsers require logging, so owners can detect mis-issuance.

**Q:** Session IDs vs session tickets?
**A:** IDs: server stores state (breaks behind a load balancer). Tickets: client stores encrypted state; any server with the ticket key can resume.

**Q:** Why rotate session ticket keys often?
**A:** A leaked ticket key can decrypt tickets and sessions resumed with them, undermining forward secrecy.

**Q:** What's the risk of TLS 1.3 0-RTT?
**A:** Early data can be replayed. Only safe for idempotent requests.

**Q:** How can a backend refuse 0-RTT data?
**A:** Respond `425 Too Early` (seeing `Early-Data: 1` from the proxy); the client retries after the full handshake.

**Q:** Where is TLS's cost concentrated?
**A:** In handshakes (per connection): round trips plus public-key CPU. Bulk encryption is cheap.

**Q:** What does TLS termination at the edge buy you?
**A:** Handshake RTTs over the short user-to-edge path, L7 features at the LB, and backends spared handshake CPU.

**Q:** What does TLS passthrough give up?
**A:** The LB can't see or modify HTTP (only IP/port and SNI); every backend holds keys and does handshakes.

**Q:** What does mTLS add?
**A:** The client presents a certificate too, so the server knows which service is calling. Meshes automate issuing and rotating the certificates.
