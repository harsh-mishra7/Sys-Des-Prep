# 04 — DNS

> Part 2 — Networking & Communication · Prerequisites: topics 01, 03

Humans and config files use names (`api.example.com`); IP needs addresses (`93.184.215.14`). DNS, the
Domain Name System, is the globally distributed, heavily cached database that maps between them. It is
the first thing almost every request touches, so it sits on the critical path of everything.

It is also, quietly, one of the most important **traffic-steering** tools in system design. The answer
a DNS server gives decides which data centre, which region, or which CDN site a user reaches. And
because DNS answers are cached all over the internet, DNS also decides how quickly you can change your
mind: how fast a migration takes effect, and how fast you can fail away from a dead region.

By the end of this topic you should be able to:

1. Trace a DNS lookup from the client through stub, recursive, root, TLD and authoritative servers.
2. Explain how caching and TTLs work, and why DNS changes take effect slowly and unevenly.
3. Plan a DNS change safely, and say why DNS alone is a poor failover mechanism for individual servers.
4. Explain GeoDNS, latency-based and weighted routing, and health-checked DNS failover.
5. Explain anycast, how it differs from GeoDNS, and why it reacts faster to failures.
6. Say how DNS itself can fail, and what that does to everything behind it.

## 1. The hierarchy: a delegated, distributed database

No single server could hold every name on the internet, or take every query. DNS solves this by
splitting the namespace into a tree and **delegating** responsibility for each subtree to whoever owns
it:

```
                         . (root)
           ┌─────────────┼──────────────┐
          com           org             uk         ← TLD (top-level domain) servers
     ┌─────┴─────┐
  example      shop                                ← each domain's authoritative servers
     │
  api.example.com → 93.184.215.14                  ← the actual record
```

- **Root servers** know where the TLD servers are. There are 13 root server *names* (`a` to
  `m.root-servers.net`), but each is served by many machines around the world via anycast (section 5),
  so in practice there are well over a thousand root server instances.
- **TLD servers** (`.com`, `.org`, `.uk`) know which name servers are authoritative for each domain
  under them. They don't know `api.example.com`'s address; they know "for anything under
  `example.com`, ask `ns1.example-dns.net`".
- **Authoritative servers** for a domain hold the actual records. When you configure DNS at a provider
  (a registrar, a cloud DNS service), you're editing records on its authoritative servers.

A **zone** is the part of the tree one set of authoritative servers is responsible for. Delegation is
done with **NS records**: the `.com` zone contains NS records saying who is authoritative for
`example.com`. If those name servers live inside the zone they serve (`ns1.example.com`), the parent
also hands out their addresses (**glue records**), otherwise you'd need to resolve `ns1.example.com` in
order to find out how to resolve `ns1.example.com`.

The design choice to notice: **each organisation runs, scales and changes its own part of the tree.**
Nobody coordinates globally except at the top. This is the same move as partitioning data (topic 25):
split ownership so no single node holds everything.

## 2. Who asks whom: stub, recursive, authoritative

Three very different roles take part in a lookup:

- A **stub resolver** runs on the client (part of the OS's networking library). It is deliberately
  dumb: it sends the whole question to a recursive resolver and waits for a final answer.
- A **recursive resolver** (your ISP's resolver, public ones like `1.1.1.1` and `8.8.8.8`, a corporate
  resolver, or the resolver inside a cloud VPC or a Kubernetes cluster) does the legwork on the
  client's behalf: it walks the tree, caches everything it learns, and returns the final answer.
- An **authoritative server** answers only for the zones it owns, and gives the definitive answer. It
  doesn't go looking for anything else.

### The resolution path

A cold lookup of `api.example.com`, with nothing cached anywhere:

```
┌────────┐ 1. api.example.com?  ┌───────────────┐ 2. api.example.com?  ┌──────────┐
│ Client │─────────────────────▶│   Recursive   │─────────────────────▶│   Root   │
│ (stub) │                      │   resolver    │◀─ "ask .com servers" ─└──────────┘
└────────┘                      │               │
     ▲                          │               │ 3. api.example.com?  ┌──────────┐
     │                          │               │─────────────────────▶│ .com TLD │
     │                          │               │◀ "ask ns1.example.." ─└──────────┘
     │                          │               │
     │                          │               │ 4. api.example.com?  ┌───────────────┐
     │                          │               │─────────────────────▶│ Authoritative │
     │                          │               │◀── 93.184.215.14 ────│ (example.com) │
     │ 5. 93.184.215.14         │               │     TTL 300          └───────────────┘
     └──────────────────────────│ caches each   │
                                │ answer by TTL │
                                └───────────────┘
```

Step by step:

1. The application calls something like `getaddrinfo("api.example.com")`. The stub checks local
   sources first (the `hosts` file, an OS-level cache if there is one), then sends a **recursive
   query** to its configured resolver: "give me the final answer".
2. The recursive resolver checks its cache. On a miss it asks a root server, which replies with a
   **referral**: "I don't know, but here are the `.com` servers."
3. It asks a `.com` server, which refers it to `example.com`'s authoritative servers.
4. It asks an authoritative server, which returns the record and its **TTL**.
5. The resolver caches every answer and referral it received, each for its own TTL, and returns the
   final answer to the client.

The questions the resolver asks in steps 2–4 are **iterative queries**: each server answers with what
it knows (an answer or a referral) and the resolver does the following. The stub's single question is
**recursive**: someone else does the walking.

In practice the root and TLD referrals are almost always already cached (their TTLs are a day or two
and every resolver needs them constantly), so **a typical cache miss costs one round trip from the
resolver to the authoritative server**, plus the client-to-resolver round trip. A cache hit at the
resolver costs only the client-to-resolver round trip, which is why public resolvers are themselves
anycast to sit close to users.

### Transport: mostly UDP

DNS queries normally go over **UDP** port 53: one small question, one small answer, no handshake, and
no per-client connection state on servers that answer millions of clients (topic 03). If a reply is
lost, the stub just times out and retries, possibly against another server. This is also why DNS
timeouts show up as strange round-number latencies (a 1 s or 5 s stall) when a resolver drops a packet.

When an answer is too large for a UDP reply, the server sets a "truncated" flag and the client retries
over **TCP**. Zone transfers between servers also use TCP. Newer variants, **DNS over TLS (DoT)** and
**DNS over HTTPS (DoH)**, encrypt the stub-to-resolver hop for privacy.

## 3. Caching and TTLs

Every record carries a **TTL** (time to live, in seconds). Anyone who caches the answer may reuse it
until the TTL expires. Caches exist at many levels:

```
Application / runtime cache ─▶ OS stub cache ─▶ Recursive resolver cache ─▶ (authoritative)
   (some runtimes cache              (some OSes)        (shared by everyone
    forever by default)                                   using that resolver)
```

Caching is what makes DNS scale to the whole internet: the authoritative server for a popular name
sees only a tiny fraction of the lookups, because resolvers answer most of them from cache. It also
creates the central trade-off:

| | Long TTL (hours) | Short TTL (30–60 s) |
|---|---|---|
| Lookup latency | Mostly cache hits, fast | More misses, slower |
| Load on authoritative servers | Low | High |
| Resilience if your DNS provider is down | Cached answers keep working for a while | Clients fail sooner |
| How fast a change takes effect | Slow: old answers linger up to the TTL | Fast |
| Usefulness for failover | Poor | Better |

Common practice: long TTLs (an hour to a day) for records that rarely change, short TTLs (30 s to 5
min) for records used to steer or fail over traffic.

### Why DNS changes are slow to propagate

"Propagation" is a slightly misleading word. Nothing is pushed anywhere. You change the record on the
authoritative server instantly; what takes time is **every cache in the world independently expiring
its old copy**. Each resolver cached the old answer at a different moment, so the switchover is
gradual, not a single cut-over. And several things make it slower than the TTL suggests:

- **TTL clamping.** Some resolvers enforce a minimum TTL or cache longer than told.
- **Application caching.** Some runtimes and libraries resolve a name once and cache the address for
  hours or until the process restarts (older Java defaults are the classic example).
- **Open connections never re-resolve.** DNS is consulted when a connection is *opened*. A client with
  a keep-alive or pooled connection to the old IP (topic 03) keeps using it until that connection
  closes, which may be hours later.
- **Negative caching.** "This name doesn't exist" (NXDOMAIN) is cached too, for a time set in the
  zone's SOA record. If something looks up a name *before* you create it, the "doesn't exist" answer
  can stick around after you create it.
- **Changing name servers** (moving a domain to a new DNS provider) involves NS records in the parent
  zone, which often have TTLs of a day or two.

### Planning a change: lower the TTL first

To move `api.example.com` to new servers when its TTL is 86,400 s (one day):

```
T − 1 day+   Lower TTL from 86,400 to 60.        (caches still hold the old 1-day TTL copy)
T            All 1-day copies have expired.       Every cache now refreshes at least every 60 s.
T            Change the record to the new IP.     Most clients move within a minute or two.
T + days     Keep the old servers running.        Stragglers: clamped TTLs, app caches, open connections.
T + later    Raise the TTL again.
```

The key step is waiting **at least one full old TTL** after lowering it. Lowering the TTL and changing
the record at the same moment does nothing for caches that already hold a one-day copy.

### The lesson: DNS failover is coarse and slow

Removing a dead server's IP from DNS doesn't stop traffic going to it: cached answers keep pointing at
it until they expire, misbehaving caches hold on longer, and established connections stay put. Very
short TTLs help but increase lookup latency and load, and don't fix misbehaving caches. And DNS has no
view of per-request health: it hands out addresses, then it's out of the picture.

So the usual division of labour is:

- **DNS** steers traffic between **regions or sites**, over seconds to minutes, coarsely.
- A **load balancer with health checks** (topic 09) removes a dead **server** in seconds, precisely,
  because it sits on the request path.
- **Anycast** (section 5) handles fast failover between sites without involving DNS caches.

## 4. Records, and DNS as a traffic-steering tool

### Record types you'll meet

| Type | Maps | Notes |
|---|---|---|
| **A** | name → IPv4 address | |
| **AAAA** | name → IPv6 address | |
| **CNAME** | name → another name | "Look up that name instead." Adds another lookup. Not allowed at the zone apex (`example.com` itself), which is why providers offer non-standard **ALIAS/ANAME** records that resolve the target server-side. |
| **NS** | zone → its authoritative name servers | How delegation works. |
| **SOA** | zone → administrative info | Includes the TTL used for negative caching. |
| **MX** | domain → mail servers | |
| **TXT** | name → arbitrary text | Domain ownership proofs, email security (SPF, DKIM), certificate validation (topic 05). |
| **SRV** | service → host + port | Used by some service-discovery systems. |
| **HTTPS / SVCB** | name → connection hints | Can advertise supported protocols such as HTTP/3 before connecting (topic 06). |

CNAMEs are how most sites point at a CDN or a managed load balancer: `www.example.com CNAME
example.cdn-provider.net`. The provider controls what that target name resolves to, and can change it
at will.

Why no CNAME at the apex? A CNAME means "this name is an alias, it has no records of its own", but the
apex must hold the zone's NS and SOA records. The two can't coexist, so ALIAS-style records exist to
fake it.

### Round-robin DNS

A name can return **several A records**. Resolvers and clients typically rotate or shuffle them, and
clients usually try them in order, which gives crude load spreading (**round-robin DNS**). It's crude
because:

- DNS doesn't know whether a server is healthy or busy.
- Caches hand the same answer (often in the same order) to many clients.
- Clients don't all behave the same way: some pick the first address, some try others on failure,
  some stick to one address for the lifetime of a process.

It's a reasonable way to spread load across several **load balancers**, each of which is itself highly
available (topic 09). It's a poor way to spread load across individual app servers.

### Answering differently for different clients

The authoritative server chooses what to answer, so it can give **different answers to different
clients** and different answers over time. This is **DNS-based load balancing**:

- **GeoDNS**: answer based on where the query seems to come from. European users get the European data
  centre's IP, Asian users get the Asian one.
- **Latency-based routing**: answer with the region that has the lowest measured latency from the
  querying network.
- **Weighted routing**: send 90% of answers to one target and 10% to another (useful for gradual
  migrations and canaries; the split is approximate, because one cached answer serves many users).
- **Health-checked failover**: the DNS provider runs health checks against each target and stops
  handing out an address whose checks fail. Combined with short TTLs, this is how many systems fail
  over between regions (topic 48), with recovery measured in minutes rather than seconds.

```
            query from resolver in Frankfurt     ┌─────────────────────┐
  ─────────────────────────────────────────────▶ │ Authoritative DNS   │
  ◀──────────── 198.51.100.10 (eu-west), TTL 60 ─│ geo table + health  │
                                                 │ checks per region   │
            query from resolver in Tokyo         │  eu-west   healthy  │
  ─────────────────────────────────────────────▶ │  ap-ne     healthy  │
  ◀──────────── 203.0.113.20 (ap-ne),  TTL 60 ── │  us-east   FAILING  │
                                                 └─────────────────────┘
```

**The blind spot: the authoritative server sees the resolver, not the user.** If a user in Mumbai uses
a public resolver whose nearest instance is in Singapore, or a corporate resolver located at the head
office on another continent, they look like they're in Singapore or at the head office. The **EDNS
Client Subnet (ECS)** extension lets resolvers pass along part of the client's address (for example
the first 24 bits) so the authoritative server can choose correctly. The costs: some privacy leakage,
and the resolver must now cache a separate answer per client subnet, which lowers its hit rate.

## 5. Anycast

GeoDNS gives different *addresses* to different users. **Anycast** gives everyone the **same address**,
and the network itself delivers each user to the nearest location.

How it works: many sites around the world announce the same IP prefix to the internet's routing system
(**BGP**, the protocol networks use to tell each other which addresses they can reach). Each router
picks what it considers the best path to that prefix, so packets from Paris naturally land at the Paris
site and packets from Tokyo at the Tokyo site.

```
           Same IP 192.0.2.1 announced from every site

   User in Paris ──▶ router ──▶ ┌──────────────┐
                                │ Site: Paris  │
                                └──────────────┘
   User in Tokyo ──▶ router ──▶ ┌──────────────┐
                                │ Site: Tokyo  │
                                └──────────────┘
   User in NYC   ──▶ router ──▶ ┌──────────────┐
                                │ Site: NYC    │
                                └──────────────┘

   Tokyo site fails → it withdraws its announcement → Tokyo routers
   now prefer the next-best path (e.g. Singapore). No DNS change needed.
```

| | GeoDNS | Anycast |
|---|---|---|
| Who decides the location | Your DNS server, at lookup time | Internet routing (BGP), per packet |
| Address users see | Different per region | One address everywhere |
| Reaction to a site failing | Limited by DNS TTLs and client caching | Site stops announcing the route; traffic shifts in seconds to minutes as routes update |
| Precision | Based on the resolver's location (may be off) | "Nearest" in routing terms, which usually but not always means geographically near |
| Control | Fine-grained: weights, per-country rules | Coarse: you influence BGP, you don't command it |
| Typical users | Multi-region apps steering to regional data centres | DNS root and public resolvers, CDNs (topic 14), DDoS protection |

Anycast is also a strong **DDoS defence**: attack traffic is absorbed by whichever site is closest to
each attacker, instead of all landing on one place.

The subtle part: routes can change mid-conversation, so packets from one TCP connection could suddenly
start arriving at a *different* site that has no state for that connection, and the connection breaks.
That's why anycast was first used for short, stateless UDP exchanges like DNS. In practice routes are
stable enough that CDNs run TCP (and TLS, and HTTP) over anycast successfully, but it's a real
constraint, and one reason anycast fits short-lived request/response traffic better than very
long-lived connections.

The two are often combined: DNS (served from anycast name servers) picks a CDN or a region, and the
address it returns is itself anycast across that provider's sites.

## 6. When DNS itself fails

Because every request starts with a name, DNS is a dependency of everything, and its failures are
unusually broad:

- **Your DNS provider goes down.** Once cached answers expire, nobody can find you, even though every
  server is healthy. The 2016 DDoS attack on the DNS provider Dyn made many large websites unreachable
  this way. Defences: use **more than one DNS provider** (NS records pointing at both), and don't set
  TTLs so short that caches can't ride out a brief outage. This is the TTL trade-off again: short TTLs
  make you agile and fragile at the same time.
- **Your resolver goes down or gets slow.** Every new connection in your data centre stalls. Internal
  resolvers are critical infrastructure; local caching on hosts reduces the blast radius.
- **A bad record is published.** A typo in a record with a one-day TTL is a one-day outage for everyone
  who cached it, and you can't recall it. Changes to long-TTL records deserve the same care as code
  deploys (topic 47).
- **Lookup amplification inside clusters.** Some environments (Kubernetes is the common example)
  configure "search domains", so the stub tries several suffixed names (`api.ns.svc.cluster.local`,
  `api.svc.cluster.local`, ...) before the real one. One lookup becomes several queries, which adds
  latency and resolver load. Fully qualified names (ending in `.`) avoid it.
- **Spoofed answers.** Classic DNS has no authentication: a resolver that accepts a forged reply
  (cache poisoning) sends users to the wrong place. Random query IDs and source ports make forging
  hard; **DNSSEC** adds signatures so resolvers can verify answers came from the zone owner. TLS
  (topic 05) is the backstop: even if DNS lies, an impostor can't present a valid certificate for your
  name.

## 7. How it connects

- **Topic 03**: DNS runs over UDP for the reasons in topic 03's UDP section, and open pooled
  connections are why DNS changes don't reach existing clients.
- **Topic 05 (TLS)**: certificates bind names to keys, so a DNS answer is only trusted once TLS proves
  the server owns the name. DNS TXT records are also one way to prove domain ownership to a CA.
- **Topic 06 (HTTP)**: DNS `HTTPS` records can announce HTTP/3 support before the first connection.
- **Topic 09 (load balancing)**: DNS does coarse balancing between sites and between load balancers;
  load balancers do fast, health-checked balancing between servers.
- **Topic 10**: service discovery can be DNS-based (SRV records, cluster DNS) and inherits DNS caching
  behaviour.
- **Topic 14 (CDNs)**: CDNs are built on CNAMEs, GeoDNS and anycast.
- **Topic 48 (multi-region)**: health-checked DNS is a common region-failover mechanism, with recovery
  time bounded by TTLs.

## Common misconceptions

- **"Changing DNS takes effect in TTL seconds."** → Only for well-behaved caches. Clamped TTLs,
  application-level caching and open connections can keep traffic going to the old address for much
  longer, and the old TTL (not the new one) governs the first switch.
- **"DNS propagation means the change is being pushed around the internet."** → Nothing is pushed.
  Caches independently expire their old copies.
- **"Removing a dead server from DNS fails it over."** → Only slowly and partially. Use a health-checked
  load balancer for server failures; DNS for coarse, region-level steering.
- **"GeoDNS knows where the user is."** → It knows where the user's *resolver* is, unless EDNS Client
  Subnet is used.
- **"Round-robin DNS is load balancing."** → It's load *spreading*, without health or load awareness,
  and skewed by caching.
- **"Anycast routes to the geographically closest site."** → It routes to the best path in BGP's terms,
  which is usually, but not always, the closest.
- **"A very short TTL is always safer."** → It makes changes fast but makes you more dependent on your
  DNS provider being up, and adds lookup latency and load.

## Answers

<details>
<summary>Show answers (attempt the questions first)</summary>

**1.** The **stub resolver** on the client just forwards the whole question and waits. A **recursive
resolver** does the full lookup on a client's behalf, walking from root to TLD to authoritative
servers, caching what it learns, and returning a final answer. An **authoritative server** only answers
for the zones it owns and gives the definitive record. Your laptop's stub talks to a **recursive
resolver** (ISP, corporate, cloud, or a public one like 1.1.1.1). Your domain's records live on its
**authoritative** servers.

**2.** The stub asks the recursive resolver. The resolver asks a root server, which refers it to the
`.com` TLD servers; asks a `.com` server, which refers it to `example.com`'s authoritative servers;
asks one of those, which returns the A record with a TTL. The resolver caches each referral and the
answer, and replies to the stub. In practice, root and `.com` referrals have long TTLs and every
resolver needs them constantly, so they're almost always cached; only the final authoritative query is
a real miss.

**3.** A lookup is one small question and one small answer. UDP needs no handshake, so a lookup is one
round trip instead of two, and servers answering huge numbers of clients keep no per-client connection
state. If a reply is lost, the **client times out and retries**, possibly to another server: the
application supplies the reliability it needs. DNS uses **TCP** when a response is too big for UDP (the
server sets the truncated flag and the client retries over TCP), for zone transfers between servers,
and in encrypted variants like DNS over TLS/HTTPS.

**4.** **Lower the TTL in advance**: reduce it to something like 60 s, then wait **at least one full
old TTL (a day)** so every cache holding the long TTL has expired. Then make the change, which now
spreads within about a minute. Once stable, raise the TTL again. Keep the old servers running for a
while anyway, because traffic can still reach them: some resolvers ignore or clamp TTLs; some
applications cache DNS results for a long time or until restart; and **open keep-alive or pooled
connections keep using the old IP** without re-resolving.

**5.** DNS failover is **slow and imprecise**. After you remove the IP, clients keep using cached
answers until the TTL expires, longer for caches that ignore TTLs, and existing connections stay on the
dead server. A very low TTL helps but increases lookup latency and load, and still doesn't fix
misbehaving caches. DNS also has no idea about per-request health. Use a **load balancer with health
checks** for fast failover between servers (seconds), and DNS for coarse steering between regions.

**6.** **Negative caching.** The resolver cached the NXDOMAIN ("doesn't exist") answer from the earlier
lookup, for a duration set by the zone's SOA record. Until that expires, users of that resolver keep
getting "not found" even though the record now exists. Lesson: create records before anything queries
them, and know your zone's negative TTL.

**7.** GeoDNS sees the **recursive resolver's** IP address, not the user's. If the user uses a public
resolver whose nearest instance is in Singapore (or a corporate resolver located elsewhere), the
authoritative server thinks the user is in Singapore. The **EDNS Client Subnet** extension lets the
resolver pass part of the user's address so the authoritative server can choose correctly. Costs: some
privacy leakage, and lower resolver cache hit rates because answers must be cached per client subnet.

**8.** **GeoDNS** hands *different IP addresses* to different users based on their (resolver's)
location, at lookup time. **Anycast** gives *everyone the same IP*, announced via BGP from many sites,
and internet routing delivers each packet to the nearest site. **Anycast reacts faster**: a failing
site stops announcing the route, and routers shift traffic to the next-nearest site as routes update,
with no DNS caches involved. GeoDNS failover waits on TTLs and client caching.

**9.** With anycast, routing decides per packet where traffic goes. If routes change mid-connection,
later packets of a TCP connection can land at a different site that has no state for it, and the
connection breaks. DNS over UDP is a single stateless request and reply, so it doesn't care. CDNs use
anycast for TCP anyway because in practice internet routes are stable over the lifetime of most
connections, and HTTP request/response traffic is short-lived enough that occasional breakage (followed
by a reconnect) is acceptable.

**10.** Clients that cached the dead server's address fail (or, if their client library tries the next
address, suffer a connect timeout first). Clients pinned to the overloaded server see slow responses.
Nothing rebalances: DNS doesn't know about health or load, caches keep handing out the same answers, and
clients don't re-resolve while connections are open. The fix is a load balancer (topic 09) in front of
the servers, with DNS pointing at the load balancer(s).

**11.** Within seconds of the outage starting, cached answers expire everywhere, and nobody can resolve
your name: the whole site is down even though every server is healthy. With longer TTLs (say an hour),
most clients would have kept working off cached answers through most of the outage. Better protection:
**use two independent DNS providers** (NS records for both), and use short TTLs only on records that
genuinely need fast changes.

**12.** A CNAME says "this name is an alias and has no records of its own", but the apex must have the
zone's NS and SOA records, so a CNAME there would conflict. Providers offer **ALIAS/ANAME** (or
"CNAME flattening") records: the authoritative server resolves the target itself and returns ordinary A
or AAAA records for the apex.

**13.** Weighting applies to **DNS answers**, not to users or requests. Each answer is cached by a
resolver and then served to everyone behind it for the TTL. A large ISP resolver or a corporate
resolver that happened to receive the "new region" answer sends thousands of users there until its
cache expires, then may flip. Big resolvers make the split lumpy, and client-side caching and
long-lived connections smear it further.

</details>

## Flashcards

Cover the answer, say it out loud, then check.

**Q:** What is DNS, in one line?
**A:** A globally distributed, heavily cached, delegated database mapping names to addresses (and other records).

**Q:** What do root servers know?
**A:** Where the TLD servers are.

**Q:** What do TLD servers know?
**A:** Which name servers are authoritative for each domain under that TLD.

**Q:** What is a zone and how is it delegated?
**A:** The part of the tree one set of authoritative servers owns; the parent delegates it with NS records (plus glue if needed).

**Q:** Stub vs recursive resolver vs authoritative server?
**A:** Stub forwards and waits. Recursive does the lookup for clients and caches. Authoritative holds the definitive records for its zones.

**Q:** DNS resolution path for a cold lookup?
**A:** Stub → recursive resolver → root → TLD → authoritative → answer cached by TTL at each level.

**Q:** Recursive vs iterative query?
**A:** Recursive: "give me the final answer" (stub to resolver). Iterative: "tell me what you know" (resolver to each server, following referrals).

**Q:** What does a typical DNS cache miss cost?
**A:** Client-to-resolver round trip plus one resolver-to-authoritative round trip (root and TLD are usually cached).

**Q:** Why does DNS use UDP, and when TCP?
**A:** One small question and answer, no handshake or per-client state. TCP for truncated (large) answers and zone transfers.

**Q:** The DNS TTL trade-off?
**A:** Long TTL: fast lookups, low load, resilient to provider outages, slow changes. Short TTL: fast changes, more lookups and load, more fragile.

**Q:** What does "DNS propagation" actually mean?
**A:** Caches everywhere independently expiring their old copies. Nothing is pushed.

**Q:** How do you safely change a DNS record with a 1-day TTL?
**A:** Lower the TTL, wait at least one old TTL, change the record, keep old servers up a while, then raise the TTL again.

**Q:** Why is DNS-based failover slow?
**A:** Cached answers until TTL expiry, caches ignoring TTLs, apps caching IPs, and open connections never re-resolving.

**Q:** What's negative caching in DNS?
**A:** "Name doesn't exist" (NXDOMAIN) answers are cached too, for a time set by the zone's SOA record.

**Q:** Why can't a CNAME be at the zone apex?
**A:** The apex must hold NS and SOA records, and a CNAME can't coexist with other records. Providers offer ALIAS/ANAME instead.

**Q:** What's wrong with round-robin DNS as load balancing?
**A:** No health or load awareness, caching skews the spread, and clients behave inconsistently.

**Q:** Name four DNS traffic-steering policies.
**A:** GeoDNS, latency-based, weighted, health-checked failover.

**Q:** What is GeoDNS, and its main blind spot?
**A:** Answering with a region-specific IP based on location. It sees the resolver's location, not the user's (EDNS Client Subnet helps).

**Q:** What does EDNS Client Subnet cost?
**A:** Some privacy, and lower resolver cache hit rates (answers cached per subnet).

**Q:** What is anycast?
**A:** The same IP announced via BGP from many sites; routing delivers each user to the nearest one.

**Q:** Why does anycast fail over faster than GeoDNS?
**A:** A failing site withdraws its route and routers shift traffic; no DNS caches have to expire.

**Q:** What's the risk of anycast for TCP?
**A:** A route change mid-connection can deliver packets to a site with no state for the connection, breaking it.

**Q:** Who uses anycast?
**A:** DNS root servers, public resolvers, CDNs, DDoS protection.

**Q:** How do you protect against your DNS provider going down?
**A:** Use two independent providers, and avoid needlessly tiny TTLs so caches can ride out short outages.

**Q:** Division of labour between DNS and load balancers?
**A:** DNS: coarse steering between regions or sites, over minutes. Load balancer: health-checked failover between servers, in seconds.
